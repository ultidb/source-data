99.1% of the corpus converts cleanly and validates against the wire schema.

## All 53 failures have one cause: duplicate team names within a division

Not the failure mode the design doc predicted. "Game references a team absent
from the roster section" — the `findRosterByTeamName` panic case — occurs
**zero** times in the real corpus. Instead every failure is
`duplicate team name (case-insensitive)`.

The failing files are listed in `duplicate-team-name-events.txt`. They span ten
seasons, so this is a persistent scraper behavior, not a one-off:

| 2014 | 2015 | 2016 | 2017 | 2018 | 2019 | 2021 | 2022 | 2023 | 2026 |
|------|------|------|------|------|------|------|------|------|------|
| 9 | 7 | 4 | 6 | 4 | 9 | 7 | 4 | 2 | 1 |

Two flavors:

**a) Two genuinely different teams sharing a display name (40 files).** The
scraper dropped an `(B)` / `(C)` suffix it otherwise captures correctly.

Worked example — `csv/2022/Midwest-Throwdown-2022CollegeWomen.csv`:

```
line 307:  Wisconsin,5      <- seed 5,  plays Pool D
line 550:  Wisconsin,27     <- seed 27, plays Pool G
```

Different seeds, different pools, different bracket placements (`Pre-Quarters`
vs `29th`). These are unambiguously two teams. The same file correctly records
`Washington University (B)` and `Wisconsin-Eau Claire`, so the convention
exists — it just failed for these rows.

**b) The scraper's own fallback string colliding with itself (13 files).**
Two or more teams literally named `TEAM_NAME_NOT_FOUND`, e.g.
`csv/2026/PLU-BBQ-2026CollegeWomen.csv`.

## Why this matters: it is already corrupting production

This is not a new restriction the validator invented. Trace today's ETL:

1. `createOrMatchTeamByName` matches on `lower(name) + division + gender`, so
   both roster blocks resolve to **one** `Team` row.
2. `creatOrMatchRosterByTeamAndTournament` matches on `tournament_id + team_id`,
   so the second block finds the first block's `Roster` and creates nothing.
3. `findRosterByTeamName` returns the first match for every game.

Net effect: the two teams silently merge, and one team's win/loss record
absorbs the other's games. In the Wisconsin example, a Pool D team and a
Pool G team share a single roster row. This has been happening since 2014.

The validator did not break these 53 events — it detected that they were
already broken.

## Recommendation

**Keep the uniqueness check strict.** Loosening it to let these convert would
re-encode the existing corruption into the new format, which is precisely what
the migration is meant to stop. This follows the same principle the design doc
applies to `Division == Other`: make the silent failure loud.

Resolution path, in preference order:

1. **Fix at the source.** Find why `(B)` suffixes are dropped for these rows in
   `parse.py`'s team-link handling and re-scrape. This fixes flavor (a) properly
   and prevents recurrence. Flavor (b) also needs the root cause of
   `TEAM_NAME_NOT_FOUND` addressed.
2. **Disambiguate on ingest** as a fallback — suffix duplicates by seed order
   (`Wisconsin`, `Wisconsin (2)`). Mechanical, but invents a team name that
   never appeared upstream, so prefer (1).
3. **Quarantine.** Convert the other 5722 and leave these 53 on the legacy path
   until (1) lands.

Whichever path is chosen, these 53 events should be re-verified during the
Phase 3 shadow diff, since their current database rows are wrong.
